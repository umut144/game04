# game04 Tasks

This file tracks only current, next, blocked or deliberately deferred outcomes.
Completed implementation history stays in Git.

**What belongs here, and what does not.** Three documents carry three different
kinds of open question, and they must not be copied into each other:

- `GAME_DESIGN.md` §15 holds the open **rules** questions — what a mechanic
  does. They are answered in the gate that needs them, and the answer goes back
  into the design document.
- `ROADMAP.md` holds the **plan**: the gates, their order, and the working
  method. It is not a tracker.
- This file holds the open **work**: decisions the implementation has to make,
  findings that need acting on, and what was deferred on purpose.

A rule question that turns out to need engineering gets a row here as well; a
row here that turns out to be a rule question moves to §15 instead.

Read `AGENTS.md` first — its rules are what every row has to stay inside.

**Where this stands.** The G00 spec round is settled (decisions `CORE-01`
through `CORE-12` below, under **Settled**). `Cardgame.Core` and the rest of
the solution shells now exist with G00's tests in place. In G01 the board geometry is settled (`LAYOUT-01`, `docs/BOARD_DESIGN.md`) and PolyTools's singles are synced into `src/Cardgame.Client/assets/polytools/` (`SYNC-02`); the totem layout, slot occupancy and the board screen with the synced PolyTools art are built (`G01-01` to `G01-06`). **G01 is done**; G02 (cards and the value language) is next. ## Settled, recorded so it is not re-litigated

| ID | Area | Decision |
|---|---|---|
| `ENGINE-01` | Platform | **Godot 4 with a C# core**, decided 2026-09-14. Server cost, the developer's first concern, turned out not to be a factor: a turn-based card game's server is a command validator with no tick loop, so Rust's advantage lands on a base of a few dozen kilobytes per match. Three things decided it instead. PolyTools is Godot and exports `.tscn`, which Godot reads directly while Bevy needs the importer world01 had to build. The product is largely presentation — animation, shaders, layered card state — and Godot ships what would otherwise be built by hand. And for agent-driven work, Bevy's API churn and compile times cost more than C# gives up, which for a turn-based game with no concurrency is little. world01 stays Bevy; a MOBA with its own simulation is a different product. Note what this does *not* decide: the engine binds only the presentation half, because the rules live in an engine-free core. **Pinned to Godot 4.7.1**, the version SceneMaker runs, so the two Godot projects stay on one SDK: `Godot.NET.Sdk/4.7.1` in the root project, `net9.0` from `Directory.Build.props`. |
| `WEB-01` | Platform | No browser client for now — the developer's goal is not the browser, which is what settled Godot with a C# core. The architecture keeps the door open rather than closing it: the client resolves no rules (`AGENTS.md`), so a thin client in another language could render snapshots without the rules engine ever shipping to it. Reopen only with the product decision, never as a technical drift. |
| `CORE-01` | Architecture | **Core models only the turn clock's logical shape (seconds/ticks as data); Server owns the real wall-clock deadline and the scheduler that enforces it**, decided in the G00 spec round. Server-authoritative absolute deadlines checked by one shared scheduler (a priority queue / timing wheel over every match, not one timer per match) is what lets a server host hundreds of matches without trusting client-reported time (anti-cheat) or paying for one OS timer per match. Core must never call a wall clock or it stops being deterministically testable. G00 ships `Cardgame.Core.Clock.TurnClock` as a bare data type reserving the shape; the real deadline, scheduler and `TurnTimedOut` production are Server's job, built when G04 needs them. |
| `CORE-02` | Architecture | **Full-state snapshot, not deltas.** The whole match state is small (6 slots × 2 sides, 3×2 totem columns × 2 sides, hand ≤ 8, a few dozen deck cards), so bandwidth is not a real concern; full snapshots win instead on robustness — trivial reconnect, no delta-desync risk, tests/dumps compare a complete expected state. A separate, fine-grained Event stream (already on the roadmap) carries "what changed" for presentation/animation — a different problem from delta-compression, not needed in G00. Alongside this: **Hand is its own zone with an explicit visibility rule**, like Deck (order and contents hidden from both sides, owner included) and Destroyed (public) — modelled from G00 even though Hand stays empty until G02+, because CORE-02 itself says visibility "cannot be retrofitted". |
| `CORE-03` | Architecture | **One root seed for the whole match.** Purpose-keyed sub-seed derivation (`SeedDerivation.DeriveSubSeed(rootSeed, purpose)`) turns it into as many independent streams as needed. Perfect Mirror derives one sub-seed per purpose and uses it on both sides (bit-identical deck order); Shuffled Mirror derives a distinct sub-seed per side (independent order). Each stream is a `Xoshiro256StarStar` instance, not `System.Random` — .NET's own `Random` is not a stable, documented sequence across versions and cannot promise "both sides provably get the same order". `REPLAY-01` is not a priority for the developer, but this contract gets it almost for free regardless. |
| `CORE-04` | Architecture | Assembly and test framework naming confirmed as proposed: **`Cardgame.*`, xunit with `Microsoft.NET.Test.Sdk`.** |
| `CORE-05` | Architecture | **A minimal, empty `project.godot` and `Cardgame.App.csproj` (Godot.NET.Sdk/4.7.1, renamed to `Cardgame.Client` by `CORE-12`) are created in G00**, not deferred to G01, so the solution's project layout (`AGENTS.md`) is final from the start and `check.sh` builds the real project tree from day one. It shows nothing; the first real scene is G01's. |
| `CORE-06` | Architecture | **All five projects from the `AGENTS.md` table, plus TestSupport, are created in G00** as (mostly) empty shells: `Cardgame.Core` (real content), `Cardgame.Server`, `Cardgame.App` (now `Cardgame.Client`, `CORE-12`), `Cardgame.Cli` (near-empty, referencing Core), `tests/Cardgame.Core.Tests` and `tests/Cardgame.TestSupport` (real content). Nobody outside Core benefits from a partially-built solution, and G00 is cheap to get the shells right once. |
| `CORE-07` | Architecture | **A card definition carries three parallel tiers, each with its own cost/bounty/attack/health, plus a list of ability name keys** — data only, no behaviour (`AGENTS.md`: "card behaviour is data, never a per-card script"). Ability behaviour is resolved by key against a separate abilities catalog, not inlined on the card. |
| `CORE-08` | Architecture | **A `design/` folder at the repository root holds one JSON file per card (`design/cards/<id>.json`) and one per ability (`design/abilities/<name-key>.json`)**, each carrying an explicit `schema_version`. `Cardgame.Core.Design.DesignCatalogLoader` parses and validates them — schema version, required tier count, non-negative corner values, and a cross-check that every card's ability name keys resolve to a real ability — into `Cardgame.Core.Model.CardDefinition`/`AbilityDefinition`, which is what Systems actually consume. Lives as a `Cardgame.Core.Design` namespace inside `Cardgame.Core` rather than a separate project: every consumer of card data (`Server`, `Client`, `Cli`) already depends on `Core`, so a 6th assembly would not reduce anyone's dependency footprint. Modelled after the `design` crate in `world01` (JSON-per-object, `schema_version`, key-based cross-referencing, tests that pin parsed values). `design/` ships empty of real content in G00 — Rogue and Wizard are G02's job; G00's own tests use fixture cards from `Cardgame.TestSupport.TestCardDesigns` instead. |
| `CORE-09` | Architecture | **Board geometry only for totems in G00.** Each side gets three anonymous `TotemColumnPair` placeholders (columns 1–2/3–4/5–6) with no identity or HP yet. Which totem (Life/Mana/Time) sits in which pair, and its randomisation, is G01's "totem placement" work, not G00's. |
| `LAYOUT-01` | G01 / Board | **Board grid geometry, settled 2026-09-15** after four rounds on the client, all written up in `docs/BOARD_DESIGN.md`. Chosen: 7:10 cards and 5:4 totems, the field filling the full height, and each side margin exactly one card wide (hand left, deck right). At the 1920×1200 reference: cards 240×342.9, totem rows 257.1 with a 321.4×257.1 totem centred in a 480-wide cell, field 1440×1200; columns, cards and side margins are each 1/8 of the width. Found by sizing the cards before scaling (224×320, totems 300×240) so that the 15/14 scale to the full height leaves exactly one card in each margin. Chosen over the 60×90 layout scaled by 10/9 and the 70×100 layout scaled by 45/43 because the widths come out exactly and the totems grow slightly with the cards. Cards and totems are drawn at 96 % of their cell, centred, so outlines keep off the cell edges (`cell_fill` in `design/asset_presentation.json`). Lives in `BoardLayoutSpec.cs`. |
| `CORE-10` | Architecture | **Starting hand is not dealt in G00.** `MatchSetupSystem` builds and shuffles both decks and stops there; the `Hand` zone exists but stays empty. Drawing a starting hand needs both real cards (G02) and a draw rule (G04, "draw 1 per round"), so it is deferred to whichever of those gates first needs it rather than guessed at now. |
| `CORE-11` | Architecture | **`Cardgame.Core.Diagnostics.WorldStateDumper` is a pure test/debug helper**, called from test assertions. It is not a program a developer runs by hand — no Cli behaviour was built for it in G00. |
| `CORE-12` | Architecture | **`Cardgame.App` is renamed `Cardgame.Client`** (folder, `.csproj`, assembly, namespace), decided 2026-09-15. macOS treats any folder ending in `.app` — case-insensitively — as an application bundle, so Finder showed `src/Cardgame.App` as a program that could not be opened. The `Cardgame.*` convention from `CORE-04` is unchanged. |
| `SYNC-02` | Assets / Tooling | **How PolyTools assets reach game04**, decided 2026-09-15. PolyTools syncs every **single** of every asset type (no sets, no palettes) from `worlds/world01/` — game04 shares that World; `POLYTOOLS_WORLD_DIR` stays overridable — into `src/Cardgame.Client/assets/polytools/<type>/<key>/manifest.json` plus `catalog.json`, and the result is **committed**, like world01's. Taking everything rather than a filtered list is deliberate: a card is a composition (the card prop plus a character), made in game04, and the set of assets it needs will grow. The sync refuses a single that references a set or palette, since those are not synced. The run is independent of world01 and SceneMaker in both directions: its own orchestrator (`sync_game04_consumers.sh` in PolyTools) calling `scripts/sync_polytools_assets.sh` here, started by the same button as a separate process. **`assets/` holds what PolyTools delivers, `design/` holds what game04 decides** — including which asset a thing uses. The sync only *reads* `design/asset_keys.json` (card frame and totems) and, from G02, each card's own key in `design/cards/*.json`, and refuses to swap when one of those keys was renamed or withdrawn. It never writes into `design/`. |
| `G01-01` | G01 / Board | **Both sides count in the same direction, and each client mirrors its view instead of turning it**, decided 2026-09-15. Slots run 1–6 from the left on both sides and slot n opposes slot n, as `GAME_DESIGN.md` §3 already says; the three totem places are named A, B, C (columns 1–2, 3–4, 5–6), the same on both sides, so A opposes A — what differs between sides is which totem stands on a place. A physical table would give the opponent 6–1 from where you sit, but then every rule that says "opposite" or "behind" needs a conversion, and the two players would name the same column differently. `BoardGeometry` holds the opposite slot, a slot's neighbours and the totem place behind a column, built now although G05/G06 are the first users. |
| `G01-02` | G01 / Board | **Totem layout**: each side's three totems are a shuffle of Life/Mana/Time over places A/B/C, from the match seed under the purpose `totem-layout` — one label for both sides in Perfect Mirror (same layout), one per side in Shuffled Mirror. Independent rolls may coincide (1 in 6), and that is accepted. Its own stream, so decks never move totems. Each side keeps its own copy, so the Stamina 3 rule (§2, G09) can later change one side alone. |
| `G01-03` | G01 / Board | **Player views are copies told from the viewer's side** (`OwnBoard`/`OpponentBoard` as `BoardSideView`), not a reference to the live board — a view taken once no longer changes when the world does, which is what `CORE-02`'s full snapshot means. |
| `G01-04` | G01 / Board | **Blank cards and a local dev match for G01's presentation.** `PlaceBlankCardCommand` and `ClearSlotCommand` put an id-only card on a free slot and take it off again, without hand or cost; bad input comes back as `CommandRejectedEvent`, never an exception. G02's real card play replaces them. Until a server exists, `BoardScreen` runs `MatchSetupSystem` and these commands itself and shows PlayerA's view; clicking the opponent's row places for PlayerB, R rolls a new seed, M switches the mirror mode. Totems and cards are drawn with the synced PolyTools art (`G01-05`, `G01-06`). |
| `G01-05` | G01 / Assets | **PolyTools asset reading lives in its own Godot-free project, `Cardgame.Assets`**, with `tests/Cardgame.Assets.Tests`; the client references it, `Core` stays rules-only. It parses and validates schema-23 manifests, builds drawable geometry (parent transforms chained, component pivot already baked into the vertices, asset pivot subtracted) and reads `design/asset_presentation.json`. Its tests also check the real files: every key in `design/asset_keys.json` has a presentation and a synced manifest, the card comes out 67.2×96 cm, every totem 72 cm tall. Alternatives were a namespace inside `Core` (testable, but presentation data in the rules library the server ships) or code inside the client (not testable at all). |
| `G01-06` | G01 / Assets | **PolyTools is the source of truth for proportions; game04 applies constant x/y factors per asset** (`design/asset_presentation.json`), and the scaled result is game04's truth — as SceneMaker scales the totems by 5 for world01. Card 1.12 / 16⁄15 (60×90 → 67.2×96 cm, stretched to the 7:10 slot), totems 9⁄16 uniformly (footprint 160×128 → 90×72 cm). One pixels-per-meter factor for the whole board: a card fills a column. Colours from the same file: card strokes crystal blue, totem strokes Life bordeaux, Mana sky blue, Time emerald, all fills paper white. |
