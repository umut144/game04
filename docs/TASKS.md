# game04 Tasks

This file tracks only current, next, blocked or deliberately deferred outcomes.
Completed implementation history stays in Git.

**What belongs here, and what does not.** Three documents carry three different
kinds of open question, and they must not be copied into each other:

- `GAME_DESIGN.md` §15 holds the open **rules** questions — what a mechanic
  does. They are answered in the gate that needs them, and the answer goes back
  into the design document.
- `ROADMAP.md` holds the **plan**: the gates, their order, and the working
  method. It is not a tracker.
- This file holds the open **work**: decisions the implementation has to make,
  findings that need acting on, and what was deferred on purpose.

A rule question that turns out to need engineering gets a row here as well; a
row here that turns out to be a rule question moves to §15 instead.

Read `AGENTS.md` first — its rules are what every row has to stay inside.

**Where this stands.** The G00 spec round is settled (decisions `CORE-01`
through `CORE-11` below, under **Settled**). `Cardgame.Core` and the rest of
the solution shells now exist with G00's tests in place, pending a check run.

## Settled, recorded so it is not re-litigated

| ID | Area | Decision |
|---|---|---|
| `ENGINE-01` | Platform | **Godot 4 with a C# core**, decided 2026-09-14. Server cost, the developer's first concern, turned out not to be a factor: a turn-based card game's server is a command validator with no tick loop, so Rust's advantage lands on a base of a few dozen kilobytes per match. Three things decided it instead. PolyTools is Godot and exports `.tscn`, which Godot reads directly while Bevy needs the importer world01 had to build. The product is largely presentation — animation, shaders, layered card state — and Godot ships what would otherwise be built by hand. And for agent-driven work, Bevy's API churn and compile times cost more than C# gives up, which for a turn-based game with no concurrency is little. world01 stays Bevy; a MOBA with its own simulation is a different product. Note what this does *not* decide: the engine binds only the presentation half, because the rules live in an engine-free core. **Pinned to Godot 4.7.1**, the version SceneMaker runs, so the two Godot projects stay on one SDK: `Godot.NET.Sdk/4.7.1` in the root project, `net9.0` from `Directory.Build.props`. |
| `WEB-01` | Platform | No browser client for now — the developer's goal is not the browser, which is what settled Godot with a C# core. The architecture keeps the door open rather than closing it: the client resolves no rules (`AGENTS.md`), so a thin client in another language could render snapshots without the rules engine ever shipping to it. Reopen only with the product decision, never as a technical drift. |
| `CORE-01` | Architecture | **Core models only the turn clock's logical shape (seconds/ticks as data); Server owns the real wall-clock deadline and the scheduler that enforces it**, decided in the G00 spec round. Server-authoritative absolute deadlines checked by one shared scheduler (a priority queue / timing wheel over every match, not one timer per match) is what lets a server host hundreds of matches without trusting client-reported time (anti-cheat) or paying for one OS timer per match. Core must never call a wall clock or it stops being deterministically testable. G00 ships `Cardgame.Core.Clock.TurnClock` as a bare data type reserving the shape; the real deadline, scheduler and `TurnTimedOut` production are Server's job, built when G04 needs them. |
| `CORE-02` | Architecture | **Full-state snapshot, not deltas.** The whole match state is small (6 slots × 2 sides, 3×2 totem columns × 2 sides, hand ≤ 8, a few dozen deck cards), so bandwidth is not a real concern; full snapshots win instead on robustness — trivial reconnect, no delta-desync risk, tests/dumps compare a complete expected state. A separate, fine-grained Event stream (already on the roadmap) carries "what changed" for presentation/animation — a different problem from delta-compression, not needed in G00. Alongside this: **Hand is its own zone with an explicit visibility rule**, like Deck (order and contents hidden from both sides, owner included) and Destroyed (public) — modelled from G00 even though Hand stays empty until G02+, because CORE-02 itself says visibility "cannot be retrofitted". |
| `CORE-03` | Architecture | **One root seed for the whole match.** Purpose-keyed sub-seed derivation (`SeedDerivation.DeriveSubSeed(rootSeed, purpose)`) turns it into as many independent streams as needed. Perfect Mirror derives one sub-seed per purpose and uses it on both sides (bit-identical deck order); Shuffled Mirror derives a distinct sub-seed per side (independent order). Each stream is a `Xoshiro256StarStar` instance, not `System.Random` — .NET's own `Random` is not a stable, documented sequence across versions and cannot promise "both sides provably get the same order". `REPLAY-01` is not a priority for the developer, but this contract gets it almost for free regardless. |
| `CORE-04` | Architecture | Assembly and test framework naming confirmed as proposed: **`Cardgame.*`, xunit with `Microsoft.NET.Test.Sdk`.** |
| `CORE-05` | Architecture | **A minimal, empty `project.godot` and `Cardgame.App.csproj` (Godot.NET.Sdk/4.7.1) are created in G00**, not deferred to G01, so the solution's project layout (`AGENTS.md`) is final from the start and `check.sh` builds the real project tree from day one. It shows nothing; the first real scene is G01's. |
| `CORE-06` | Architecture | **All five projects from the `AGENTS.md` table, plus TestSupport, are created in G00** as (mostly) empty shells: `Cardgame.Core` (real content), `Cardgame.Server`, `Cardgame.App`, `Cardgame.Cli` (near-empty, referencing Core), `tests/Cardgame.Core.Tests` and `tests/Cardgame.TestSupport` (real content). Nobody outside Core benefits from a partially-built solution, and G00 is cheap to get the shells right once. |
| `CORE-07` | Architecture | **A card definition carries three parallel tiers, each with its own cost/bounty/attack/health, plus a list of ability name keys** — data only, no behaviour (`AGENTS.md`: "card behaviour is data, never a per-card script"). Ability behaviour is resolved by key against a separate abilities catalog, not inlined on the card. |
| `CORE-08` | Architecture | **A `design/` folder at the repository root holds one JSON file per card (`design/cards/<id>.json`) and one per ability (`design/abilities/<name-key>.json`)**, each carrying an explicit `schema_version`. `Cardgame.Core.Design.DesignCatalogLoader` parses and validates them — schema version, required tier count, non-negative corner values, and a cross-check that every card's ability name keys resolve to a real ability — into `Cardgame.Core.Model.CardDefinition`/`AbilityDefinition`, which is what Systems actually consume. Lives as a `Cardgame.Core.Design` namespace inside `Cardgame.Core` rather than a separate project: every consumer of card data (`Server`, `App`, `Cli`) already depends on `Core`, so a 6th assembly would not reduce anyone's dependency footprint. Modelled after the `design` crate in `world01` (JSON-per-object, `schema_version`, key-based cross-referencing, tests that pin parsed values). `design/` ships empty of real content in G00 — Rogue and Wizard are G02's job; G00's own tests use fixture cards from `Cardgame.TestSupport.TestCardDesigns` instead. |
| `CORE-09` | Architecture | **Board geometry only for totems in G00.** Each side gets three anonymous `TotemColumnPair` placeholders (columns 1–2/3–4/5–6) with no identity or HP yet. Which totem (Life/Mana/Time) sits in which pair, and its randomisation, is G01's "totem placement" work, not G00's. |
| `CORE-10` | Architecture | **Starting hand is not dealt in G00.** `MatchSetupSystem` builds and shuffles both decks and stops there; the `Hand` zone exists but stays empty. Drawing a starting hand needs both real cards (G02) and a draw rule (G04, "draw 1 per round"), so it is deferred to whichever of those gates first needs it rather than guessed at now. |
| `CORE-11` | Architecture | **`Cardgame.Core.Diagnostics.WorldStateDumper` is a pure test/debug helper**, called from test assertions. It is not a program a developer runs by hand — no Cli behaviour was built for it in G00. |
